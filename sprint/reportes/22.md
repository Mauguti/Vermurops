## Qué hice

Agregué un nodo «Valida token» al flujo `generar-pdf-cotizacion` en
`docs/n8n/generar-pdf-cotizacion.n8n.json`. El nodo lee el header
`x-vermur-token` de la petición y lo compara contra la variable de entorno
`VERMUR_N8N_TOKEN` de n8n. Si falta el token, no coincide, o la variable no
está configurada, el flujo responde 401 JSON `{ ok: false, error: 'No
autorizado.' }` sin llegar a Gotenberg. El flujo existente no se modificó:
solo se insertó el nodo entre «Recibe cotización» y «Arma el HTML», y se
desplazaron las posiciones para mantener el layout legible.

Actualicé `docs/n8n/README.md` con la documentación de seguridad, la
configuración requerida y el procedimiento de rollback.

## Decisiones que tomé y cómo se revierten

1. **Comparación con `process.env.VERMUR_N8N_TOKEN` en un Code node**, no con
   la autenticación nativa del webhook. El webhook nativo con Header Auth
   requiere crear una credencial en n8n, que no se puede versionar en git. El
   Code node es explícito, visible y versionable. Se revierte cambiando el
   nodo por la autenticación nativa del webhook y configurando la credencial
   en n8n.

2. **`onError: continueErrorOutput`** en el nodo de validación. Si el token
   falla, el `throw` redirige a la salida de error → «Rechaza sin token»
   (401). Es el mismo patrón que usan «Arma el HTML», «Gotenberg convierte»
   y «Prepara respuesta» para sus errores.
